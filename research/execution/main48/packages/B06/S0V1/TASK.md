# Task B06: enforce expiry atomically at payment completion
For a valid incoming matching-code payment of the correct amount, pending orders at or beyond expiresAt must become expired rather than completed even if cleanup has not run. Evaluate server time at the serialized decision to update that order (application or database clock is allowed), not the untrusted payload timestamp. Retain the linked payment audit; expired orders grant no entitlement. An ignored/order_not_pending response is correct for expiry, consistent with existing terminal-state responses. Live pending orders complete; mismatch, unknown and existing terminal orders keep their existing behavior. Make competing cleanup and completion safe: once expired/cancelled/completed, a row cannot be flipped back by a competing payment. For two distinct valid simultaneous payments for the same live order, at most one may report completing it; duplicate transaction IDs retain existing already_processed behavior. This atomic response rule is an explicit new requirement, not a claim about baseline correctness. Preserve existing public webhook/cron entry points, audit semantics, identity, access control, dependencies and the entitlement model.
