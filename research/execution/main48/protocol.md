# SmartKit: prospective 48-slot protocol

Prepared 16 November 2026. This protocol takes effect only with a passing technical readiness audit and its new freeze. It does not revise the historical pilot freeze. No main model session has been invoked during preparation. The current task contracts are the six entries in `task-cards.json` and their identical public `TASK.md` copies across treatment conditions.

## Question, contribution and boundary

For six fixed constructed SmartKit maintenance/extension tasks, does source organization (S) or access to an executable retained-behavior package (V) change joint success under the same agent budget? The practical decision concerns the two implemented SmartKit layouts and whether to supply this package to this agent. It does not concern all starter kits, human productivity, the value of all possible tests, or the economics of refactoring.

The contribution sought is a matched factorial case comparison with an audit of the distinction between new acceptance and retained behavior. The existing prior-work review is in `../research-direction-review/assessment.md` and `../../paper-proposal/citation-evidence.md`. Feature preservation, test context, repository interventions and fault qualification already occur in the reviewed studies. Their presence is not claimed as novelty here. This protocol does not establish an absence of identical prior work or promise publication. A null or adverse result will still be reported with its uncertainty, without a claim that a wide interval demonstrates equivalence.

## Task frame and treatment reach (G1)

| Task | Public operation and actual transport | Different organization exposure | Retained obligations exercised |
|---|---|---|---|
| A01 | Settings profile form; browser discovers actual write | Auth/session guard, profile validation and any new UI/action module have layout-specific locations | Protected fields, safe stored-name rendering, sign-in, protected settings, order reads |
| A04 | Existing registration/reset UI and auth HTTP endpoints | Shared auth configuration, client and email modules; two existing forms | Old short-password login, 128 upper bound, expired/invalid token handling and identity |
| B05 | Existing signed payment webhook, checkout and cron HTTP route | Shared payment-content parser/formatter and transaction processors | Standard checkout/QR content with exact code case, valid signed standard payments, audit/retry, amount/terminal restrictions |
| B06 | Existing signed webhook and cron HTTP route | Shared completion transaction, cleanup, entitlement reads | Live-order completion, mismatch/terminal/outbound behavior, linked audit and duplicate transaction handling |
| U02 | Detail discovered from selected admin-directory row; browser plus direct access | Shared auth/permissions/session/DB interfaces used from directory/detail | Directory authorization, aggregate counts, no token leakage and read-only identity/orders |
| U03 | Directory role control; browser captures and replays real write transport | Shared current-authority and role helpers, auth API, directory/session data | Old directory authorization/counts/token restrictions and unchanged identity/credentials/orders |

Source equivalence is audited by resolving local imports to their original module identities, not by comparing path spellings or imposing a required edit count. A04/B05/B06 change existing shared rules. A01/U02/U03 include relatively localized UI/route extensions and may have weaker S exposure. Both contrasts retain all six tasks with equal weight; this heterogeneity is declared before outcomes. Traces can describe actual reads/reuse, not prove mediation or rescue a missing effect. No task was selected using main-agent success or a preferred winning condition.

All six tasks are assistant-constructed use cases, not verified production issues. A01 has development qualification exposure but no new main-agent outcomes. History-filter smoke results remain development-only; admin filtering is development-only; other-session revocation stays on hold. Retired candidates remain in the registry with zero allocation. No automatic substitute task is allowed.

## Allowed changes, preservation and fault gate (G2)

The complete requested business rules are public. Hidden checks withhold inputs and assertions, not requirements. A04 intentionally changes password creation/reset acceptance, while preserving existing account login. B05 intentionally expands/restricts description recognition according to its public grammar and preserves standard generated content. B06 intentionally adds expiry enforcement and atomic response semantics. The live-concurrent-response diagnostic observed in the baseline is therefore a new acceptance requirement, not a preservation obligation.

V0 retains all five original commands: `check-types`, `test:run`, `test:billing`, `test:sepay-qr-url`, and `build`. The supplied unit suite contains four files and 14 tests. None is removed or weakened. V1 adds a task-specific public preservation script and command; it does not contain new-feature acceptance assertions. The hidden evaluator uses separate fixtures/assertions. A01 reuses the earlier separate visible/final instruments, with explicit navigation timeout configuration; no historical qualification count is relabeled as a new repetition.

| Task | Shared/old regression used for V-gate |
|---|---|
| A01 | Unsafe rendering of a stored display name |
| A04 | Accidentally lower maximum accepted reset password from 128 to 127 |
| B05 | Accidentally lowercase the code in standard checkout transfer content while changing parser/formatter rules |
| B06 | Expire/reject a correctly paid order that is still live |
| U02/U03 | Weaken the shared admin guard so the old directory becomes readable by ordinary users |

The two admin task/layout pairs reuse one fault template and are not independent defect types. Faults are assistant-seeded; they do not estimate the rate or kinds of errors agents will actually produce. A task passes this gate only when its fault passes all five V0 commands but fails the named old-behavior visible and hidden checks on both layouts. Baseline preservation must pass and at least one new acceptance must fail; correct reference and structurally different valid alternative must pass. No fault is inserted into the actual starting packages.

## Instrument validity and reliability (G3)

Public and hidden suites use Chromium/Playwright 1.58.2 and PostgreSQL 16. They exercise signed webhook HTTP, cron HTTP with a synthetic upstream transaction-list response, auth HTTP, and browser-discovered UI writes. No application module import is used as the final acceptance criterion. U03 replay supports ordinary URL-encoded, JSON and identifiable multipart bodies. An unsupported encrypted/bound/custom transport is recorded as unassessable and requires a measurement adapter on the same saved patch, with an instrument correction record; it is never silently labeled an agent failure.

The upstream and clock adapter is common to every condition, outside `/workspace`; agents receive its fixture interface in the public task card. It contains no acceptance assertions or task answers. It simulates SePay's transaction list only, preserving actual application parsing, HTTP cron authorization, cleanup and completion logic. Normal wall time is used except in the declared deterministic application-clock boundary check. An implementation using database decision time is allowed; exact SQL-clock equality is not imposed by an application-clock stub. No real bank/email integration is represented as tested.

For each task/layout, the final reliability ledger must contain: baseline visible 20 rounds and hidden three; reference visible/hidden 20 each; alternative visible/hidden three each. A01 uses 30 instead of 20 to retain the stricter prior target. Each checker invocation uses disjoint synthetic identities and removes its account/order fixtures; baseline and each candidate use a fresh runtime/DB. Native signature-rejection audit rows may remain within a reliability runtime until that runtime is deleted. Their accumulation is not treated as independent data or as a fresh database per round. Reliability tests repeat fixtures on that runtime rather than claiming a fresh OS/container for each round. Full V0 checks are reused only from an identical image/runtime/package/candidate with a recorded binding; their repeated execution is not necessary to count checker reliability. Faults receive one visible/hidden round plus all V0 commands. Passing 20/30 rounds is an operational stability check, not proof of a low flake rate.

Unexpected preparation errors remain archived. Changes to checker, mock, source candidate, runtime, image or package invalidate the corresponding recorded qualification. Infrastructure interruptions do not turn incomplete rounds into passes. A pre-main correction is allowed with new instrument provenance and a full relevant gate rerun; post-invocation measurement corrections replay every affected saved patch without new model calls.

## Allocation and execution

Six tasks × four cells × two repetitions = 48 scheduled slots. Blocks are task/repetition pairs. Python's `random.Random(20261115)` shuffles the twelve blocks and then the four cells in each block; the actual order is stored in `allocation.json`. Equal task weighting is fixed. Auth, billing and admin each contribute two tasks. No effect estimate is inferred from development probes.

The requested model is `gpt-6-luna`, high reasoning, default/standard service without a priority override, CLI 0.166.0, 900 seconds per invocation including the agent's own checks; there is no token cap. Model-list preflight confirms advertised access, not guaranteed availability or response success at collection time. Collection uses existing ChatGPT allowance. No paid API key, model upgrade, extra model pilot or replacement invocation is added. Maximum scheduled model wall time is 12 hours; preparation and offline scoring are separate costs.

Every slot starts from an unsolved task-specific package, freshly migrated/seeded DB, one baseline commit, no source history, no host mounts, no Docker socket, a fresh Codex home and no parent workspace rules or research files. User config, execpolicy rules, persistent memory, plugins/apps and subagents are disabled in the collection client. Ordinary coding/browser tools and dependency environment are shared. Warmup compiles the same baseline routes before the model timer and does not implement any task. Collection runs serially without qualification/build jobs competing for resources. Software image and frozen artifact records are checked before collection and again before every unstarted slot.

Invocation is recorded before starting the CLI process. Once marked invoked, a slot can never be reinvoked, even after timeout/error. Unstarted slots can resume in the fixed order after documented infrastructure recovery. A timeout patch is captured and graded; no usable patch or an interrupted scorer is recorded separately. Evaluation can be retried on the same saved patch. A hard collection stop triggers adjudication and resumes only unstarted slots; it cannot change task count or replace failures.

The disposable application container's active processes are stopped before source capture so background commands cannot continue editing after a session. The database runs in a separate container. The same shutdown/capture path is exercised in no-model rehearsals. The 900-second limit is the scheduled invocation cap; observed timing records also expose termination latency rather than hiding it.

24 no-model rehearsals must pass capture, archive, fresh-runtime reconstruction and scoring, one per task/cell. They use explicit reference sources and no account credentials. Authentication is injected only during a subsequently authorized model invocation and excluded from archives/scoring. Official CLI behavior was checked against [non-interactive mode](https://learn.chatgpt.com/docs/non-interactive-mode) and [CLI reference](https://learn.chatgpt.com/docs/cli/reference); local `--help`/version checks additionally record the actual pinned executable.

Preparation runs serially after simultaneous production builds exhausted the local Docker runtime. Within a qualification/scoring runtime, the dev server is stopped after HTTP/browser checks and before the unchanged production-build command. No-model rehearsals can reuse a full five-command V0 result only for an archived reference capture that exactly matches a qualified reference's application/configuration files, the same runtime/image and the same candidate manifest. The documented generated `next-env.d.ts` dev/build path is normalized for that comparison. Arbitrary main-agent patches always execute the full trusted V0 composite afresh. Reuse provenance remains in each rehearsal outcome.

## Outcomes, missingness and analysis

Each final patch is evaluated outside the agent runtime against trusted V0, the task's public preservation suite B1, and the withheld evaluator E. E reports acceptance E_A and retained-behavior E_P separately. Joint success requires E_A, E_P and all V0 commands, with declared dependency restrictions respected. Supplied check sources are restored for replay, so editing tests cannot buy a pass; arbitrary application helpers are retained. B1 is replayed on all four cells, including V0 sessions; access during generation remains the V treatment. Initial scoring comprises at most 144 composite suite passes (48 × V0/B1/E), with any infrastructure replays logged separately.

A changed dependency declaration violates the public dependency restriction. A changed lockfile alone triggers adjudication rather than automatic functional failure: compare resolved dependencies to distinguish prohibited environment changes from formatting-only edits, retaining the same saved patch and all original records. Scorer startup/fixture errors likewise require baseline-control diagnosis before attributing failure to an agent; unresolved outcomes remain missing. No new model invocation is allowed for either case.

Report 24 task-cell success counts with denominator two before marginal effects. Distinguish planned, invoked, patch captured, assessable, successful and missing. Missing is not automatically success or failure: report worst/best-case bounds over all planned slots. No complete-case contrast is substituted for the fixed allocation without its explicit missingness scope. Unsupported transport, fixture/evaluator failures and agent-caused build/runtime failures are distinguished from the saved evidence. All invoked attempts, including failures/timeouts, contribute to recorded cost; absent token/time data remain missing.

The primary descriptive contrasts are equal-task marginal risk differences S1−S0 and V1−V0. Two conservative simultaneous 95% Hoeffding intervals may be reported for a complete dataset conditional on independent bounded slot outcomes; the half-width at N=48 is about 0.427. These broad intervals do not establish equivalence or small-effect sensitivity. Conditional randomization tests for the sharp null of no effect of one factor at either level of the other hold the other factor and task/repetition block fixed; within-pair sign flips yield an exact binomial calculation. If reported, the two sharp-null p-values use Holm adjustment. They are not tests of a zero average effect. Interaction is descriptive and unpowered. No task-population/general-starter-kit interval is implied.

Report all six leave-one-task-out and all three leave-one-domain-out contrasts/bounds. These are sensitivity analyses of the same observations, not new independent samples. Cost is reported for every invocation alongside success uncertainty, not interpreted as efficiency at equal success when success intervals are unresolved.

The check audit compares B1 pass/fail with E_P pass/fail on jointly assessable saved patches, overall and by condition/task, with explicit denominators and missing counts. B1 pass plus E_A fail alone is not a preservation escape. Defects are labeled old/new/shared obligation, with invariant and failing path/check evidence. Traces describe navigation, edits, checks run, feedback and repairs; uncertain or unavailable reads remain unknown. One illustrative patch per task is selected by fixed allocation order: first assessable joint failure, otherwise the first assessable patch. Examples never replace aggregate counts or establish causal mediation. Independent human review/second coding is unavailable and must be disclosed.

## Release boundary (G4 and final audit)

The scoped comparison remains worthwhile if its admitted tasks and measurement gates pass, even if S/V effects later prove small, adverse or unresolved. It is not justified as a strong general design recommendation. Qualification establishes measurement feasibility and differential detection, not a positive treatment effect. The author still owns interpretation, disclosure and any later submission decision.

`audit.py --freeze` may create a new technical freeze only when 24 package audits, 48 qualification/reliability cases, 24 capture/reset/score rehearsals, runner self-check, instrument review, model preflight and this protocol are present and current. A separate explicit start release tied to that freeze is required by `collect.py run`. Preparing the study does not start the 48 runs. Source artifacts, bibliography and development results remain intact; manuscript prospective sections must agree with this protocol before start.

Before freeze, the proposed missing-space formatter fault was rejected because V0 unit tests detected it. The lowercase-code formatter fault is a separate plausible normalization regression; it is eligible only if all five V0 commands pass. Checkout fixtures rejection-sample at most eight generated codes until an uppercase input is available, without inspecting treatment success to choose the input; failure to generate that fixture is an instrument error rather than a functional result. Every attempted checkout still asserts standard formatting. No application generator or V0 test is changed.

Run these stages serially; each stops on an unexpected outcome and preserves its logs. Completed gates are reused only with matching artifact bindings.

python -X utf8 research/execution/main48/finish-preparation.py --layout layered

After the current instrument review and manuscript records are finalized and readiness reports no blockers, `audit.py --freeze` writes the technical freeze. A missing or stale author start release still prevents `collect.py run` from invoking anything. Do not run package regeneration after freeze; it refuses to overwrite frozen materials.

After a scoring infrastructure correction, `collect.py rescore --slot <allocated-slot-id>` replays only that slot's saved workspace, preserving prior outcome records. It never calls the model and cannot create an absent attempt. Generation-interruption flags remain unresolved until an explicit adjudication record settles them; a successful scorer replay alone does not erase that uncertainty.
