What Coding Agents Follow When Evolving Existing Code Haichao Zhu Geyang Xu Zhaorui Yang Jiyuan Wang Affiliation: University of California, Riverside Independent Researcher Tulane University Qian Zhang Abstract Existing code reveals past implementation decisions but rarely explains the reasoning behind them. When coding agents implement new features or modify existing functionality, past decisions may conflict with new task instructions. This raises a fundamental question for agentic software evolution: when multiple implementations satisfy the same functional requirements, how do coding agents decide whether to follow existing code or new task instructions? We investigate this question through bidirectional, controlled experiments in purpose-built repositories, followed by validation in real-world open-source repositories. Our approach isolates three competing sources of guidance: (1) Agents’ Default Preferences, measured without repository precedents; (2) Repository Precedents, examined by manipulating the frequency and location of existing code examples; and (3) Explicit Task Instructions, tested by introducing rules that conflict with existing code. We conduct 5,625 trials across four coding agents and six implementation pairs, with validation in four open-source repositories spanning three programming languages. We find that agents share the same default implementation choices, yet overwhelmingly follow repository precedent when it conflicts with those defaults (359/360 trials). Crucially, not all precedents carry equal influence: three supporting local files yield 96% adoption, compared with only 4% for sibling-resource files, and changing file placement alone can shift adoption from 0% to 100% at a fixed example count. When new task intent conflicts with existing code, written priority rules achieve substantially higher success than code examples alone (59/60 versus 38/60 joint successes for two agents on two implementation pairs). The effectiveness of explicit rules also extends to open-source repositories, where a harness-loaded rule raises joint success from 0/120 to 117/120. In controlled experiments with four agents and six implementation pairs, existing code wins by default, and a written rule is what reliably changes course. 1 Introduction Software development involves the continuous evolution of existing systems. As LLM-based coding agents take on increasingly complex software engineering tasks, their role is expanding beyond individual issue resolution to implementing changes across evolving repositories Yang et al. [2024] , Jimenez et al. [2024] , Zhu et al. [2026] , Deng et al. [2026] , Le et al. [2026] . Unlike building from scratch, extending an existing repository means working inside decisions made during earlier development, whose rationale is often lost. These decisions influence how new functionality is implemented, even when multiple alternatives satisfy the same functional requirements Deng et al. [2026] , Zhu et al. [2026] . However, existing code rarely explains why a particular implementation was chosen or whether that decision should be preserved as requirements evolve. Coding agents must therefore reconcile past implementation decisions with the intent expressed in new task specifications. Past Decisions vs. New Intent. Existing code records past implementation decisions. Every new change inherits decisions made in the past, but how does a coding agent determine which decisions to preserve, particularly when a new task expresses a different intent? This question raises two challenges in agentic software evolution. First, the rationale behind past implementation decisions is often unavailable. Existing code reveals what previous developers chose, but rarely why Liang et al. [2023] , Zhao et al. [2024] , Sharma et al. [2021] . For example, a repository may use an if-else chain rather than a dictionary lookup because of an earlier requirement or simply a developer’s preference. Without this context, a coding agent cannot determine whether the existing code reflects a constraint that should be preserved. Second, past implementation decisions may conflict with the new task intent. Different parts of a repository may follow different implementation patterns, while new task instructions may favor an alternative Wang et al. [2025b] , Li et al. [2025] . For example, an agent adding an API endpoint may encounter existing handlers that serialize identifiers as integers, while the new task may specify a preference for string identifiers. Both options may satisfy functional requirements, but represent different implementation choices. The agent must determine whether to follow the existing precedent or the new instructions. Despite substantial progress in evaluating coding agents in long-horizon software engineering tasks Jimenez et al. [2024] , Le et al. [2026] , Zhu et al. [2026] , how agents prioritize past implementation decisions and new task instructions remains poorly understood. In particular, we lack systematic evidence on the relative influence of agents’ default preferences, implementation patterns in task-related code and elsewhere in the repository, and explicit task guidance. Approach. We investigate how coding agents prioritize competing sources of guidance when modifying existing software repositories. We examine three factors: (1) agents’ default implementation preferences, (2) repository precedent established by past implementations, and (3) explicit guidance in new task specifications. Our approach combines bidirectional controlled experiments in purpose-built repositories with a validation study in real-world open-source repositories. We first establish agents’ default preferences in a manually constructed Python/Flask repository. We design six implementation-choice cases that span naming, data representation, error handling, and control flow, each allowing two functionally correct alternatives, such as integer versus string identifiers. By removing relevant repository examples, we establish a baseline for two complementary controlled interventions: • Repository Precedent. We examine how historical implementations shift agents’ default choices.
We distinguish local precedent, established by existing endpoints for the resource being extended, from sibling-resource precedent, established by endpoints for other resources in the same repository. Holding task requirements fixed, we vary the number and placement of supporting examples and introduce conflicting patterns across resources. These interventions isolate how the prevalence and location of existing patterns influence agents’ choices. • Explicit Task Guidance. We examine whether new instructions can override established precedent. Starting with code that favors one implementation, we compare four guidance conditions: no guidance, a written priority rule, a code example favoring the alternative, and both combined. We further test whether a rule reaches the agent equally well through the task description or through the harness’s native instruction file. This reveals how different forms and channels of guidance redirect agents toward a new task intent. Key Findings. Our study comprises 5,625 trials across six implementation pairs and four models: Claude Sonnet-4-6, Claude Opus-4-8, Codex gpt-5.6-sol, and Codex gpt-6-sol. We further evaluate four open-source repositories spanning Python, Go, and TypeScript: FastAPI RealWorld nsidnev and contributors [2026] , FastAPI Clean Example ivan-borovets and contributors [2026] , Go REST API qiangxue and contributors [2026] , and ExpressJS API larswaechter and contributors [2026] . Three key findings emerge, highlighting the need to make implementation decisions and their intended priority explicit during software evolution. First, repository precedent overturns agents’ shared default choices in 359/360 trials. Without relevant repository precedents, all four agents favor the same implementation in each of the six pairs. Yet when all existing endpoints consistently use the opposite implementation, agents follow that precedent in 359/360 trials, despite unchanged functional requirements. In four open-source repositories, agents follow local precedent in all 945 functionally successful, classifiable error-handling implementations and 355 of 417 (85%) functionally successful response-envelope implementations. Second, a single well-placed example can outweigh multiple examples elsewhere. With three supporting files, local precedents yield 96% adoption (347/360), compared with only 4% (13/360) for sibling-resource precedents. Even within local code, changing file placement while holding the number of examples fixed can shift adoption from 0% to 100%. In one setting, a single well-placed example even outperforms two examples in other files. These findings show that the influence of repository precedent cannot be explained by example frequency alone. Third, written priority rules override conflicting precedent more reliably than code examples alone (98% vs. 63%). When all existing endpoints favor the opposite implementation, written priority rules achieve both functional success and target adoption in 59/60 trials, compared with 38/60 for code examples alone and 0/60 without guidance. The effectiveness of written rules also extends to four open-source repositories, where a rule in the harness’s native instruction file raises joint success from 0/120 to 117/120. Although the required behavioral specification is given, some concrete implementation decisions remain open. For example, the task identifier may be serialized as a JSON number (Figure 2 (b)) or as a string (Figure 2 (c)). Past Decisions as Precedent. The existing task handler in Figure 2 (a) serializes the identifiers as numbers using task.id . Such existing implementations establish repository precedents : past implementation decisions that may guide subsequent changes. An agent following this precedent would produce Figure 2 (b). However, a repository does not necessarily follow a single implementation pattern across locations within a codebase. The two ID representations illustrated in Figure 2 (b) and (c) may coexist in existing code, appearing in different files or even within the same file. The agent may therefore encounter conflicting historical implementations rather than a single pattern to follow. New Intent. Following existing implementation decisions helps maintain consistency as software evolves. For example, reusing the numeric-ID representation in Figure 2 (a) would keep the new endpoint consistent with existing task responses. However, new requirements may require changes to earlier design choices. Suppose the new task explicitly states: “Serialize task identifiers as strings in the new endpoint. This instruction takes precedence over the ID representations used by existing handlers.” The agent now faces a conflict: following the existing precedent preserves consistency but contradicts the new instruction, whereas following the instruction satisfies the new intent but departs from the established implementations. This illustrates a fundamental challenge in software evolution: how coding agents choose between preserving past implementation decisions and following newly specified intent. The Research Problem. The resulting code reveals which implementation the agent selected, but not what guided that choice. An agent may follow its default preference, adopt a precedent found in the repository, or follow an explicit task instruction. Our research investigates how these three sources of guidance influence implementation choices, particularly when historical precedents and new task intent conflict. Within the controlled study, Stage 1 measures default choices without relevant examples, Stage 2 varies repository precedents in local and sibling-resource files (including which file holds the example at a fixed count), and Stage 3 adds task guidance that contradicts existing code. Every edit is scored separately for functional success and implementation choice; the local-versus-sibling comparison is also checked in open-source repositories. 3.1 Overview We design a three-stage controlled study that separates the sources of guidance a coding agent may follow when it extends an existing repository (Figure 3 ). The design rests on one principle: every stage keeps the functional task and its hidden tests unchanged and varies only the guidance available to the agent. A change in the agent’s implementation choice can therefore be attributed to the varied guidance rather than to a change in what the code must do. Study Object. Each study task admits two functionally acceptable implementations, which we call an implementation pair . Before running any agent, we designate one implementation as the baseline and the other as the alternative . These labels are fixed in advance and do not encode which implementation an agent prefers. Pair-specific hidden tests accept either implementation, so the functional requirements stay fixed while the implementation choice remains open. For example, in the ID serialization case, the tests verify that the returned identifier matches the expected task ID, accepting either its numeric or string representation. We study six pairs spanning naming, data representation, and code structure (Table 1 ), and use ID serialization from Section 2 as the running example: a new endpoint may serialize task identifiers as integers (baseline) or strings (alternative). All three stages use a purpose-built Flask Task Manager API. In its full form, the repository contains three endpoints for tasks (create, update, and list) and three for projects (create, update, and list), each in its own file, together with the data model, database setup, and application scaffold. The agent is asked to add a new endpoint for task , GET /projects/<id>/tasks/<id> . We therefore call the existing task endpoints local files, because they belong to the resource being extended, and the project endpoints sibling-resource files, because they implement an analogous resource that the new endpoint does not modify. Where an implementation pair requires additional functionality, we minimally extend the agent’s assignment. For example, the field-casing case additionally requires the endpoint to return the parent project ID, and the Boolean-naming case requires adding a domain-model field. Three Stages. Each stage (Figure 3 ) isolates one source of guidance. Stage 1 removes all existing endpoints to measure default choices (Section 3.2 ); Stage 2 controls how many and which local and sibling-resource files use the alternative (Section 3.3 ); and Stage 3 sets every endpoint opposite a target and supplies explicit guidance through the task description or the harness’s native instruction file (Section 3.4 ). All stages assess functional success and implementation choice, as described in Section 3.5 . 3.2 Stage 1: Establishing Default Preferences Zero-Precedent Repository. Stage 1 establishes agents’ default implementation choices without relevant repository precedents.
We remove all six existing task and project endpoint files from the controlled repository while retaining the data model, database setup, and application scaffold.
The resulting zero-precedent repository remains sufficient for implementing the new endpoint but contains no relevant endpoint examples. We construct one variant per implementation pair, retaining the necessary pair-specific task extensions. For each pair and agent, we run independent sessions on fresh repository copies, using the same functional task as in Stage 2 without prescribing an implementation choice. We classify the resulting implementations (Section 3.5 ) and define the option chosen in more than half of an agent’s sessions as its default. These defaults provide a reference for measuring the influence of repository precedent and explicit guidance in subsequent stages, independently of the predefined baseline and alternative labels. In the running example, the task model retains its integer primary key, but no existing handler demonstrates whether IDs should be returned as task.id or str(task.id) . In this setting, all four models default to returning numeric IDs ( task.id ), as confirmed by the zero-precedent results in Section 4.2 . 3.3 Stage 2: Manipulating Repository Precedents Stage 2 restores the six endpoints and rewrites the construct under study in a controlled subset of them. For ID serialization, we change an existing endpoint from "id": task.id to "id": str(task.id) ; all other code in that endpoint stays identical. The other pairs are rewritten analogously, changing only the construct under study. Throughout Stage 2, the task description asks the agent to follow the conventions of the existing code without naming the implementation choice, mirroring common contribution guidelines. Any shift toward the alternative must therefore come from the code itself. Support Level and Conditions. We call the number of files in a group (local or sibling-resource) that use the alternative the group’s support level ( k / 3 k/3 ). For each pair, we construct eight conditions (Figure 4 , upper rows): • Agreeing groups: all six existing endpoints use the baseline (“Both baseline”; 0 / 3 0/3 , 0 / 3 0/3 ) or the alternative (“Both alternative”; 3 / 3 3/3 , 3 / 3 3/3 ). • Local support: local support 1 / 3 1/3 , 2 / 3 2/3 , or 3 / 3 3/3 , with all sibling-resource files at the baseline. • Sibling-resource support: sibling-resource support 1 / 3 1/3 , 2 / 3 2/3 , or 3 / 3 3/3 , with all local files at the baseline. We call this design bidirectional because each group is varied while the other is held at the baseline, so the influence of the two groups can be compared at the same support level. Whenever one group supports the alternative, the two groups conflict; at 3 / 3 3/3 they disagree completely, and comparing local 3 / 3 3/3 with sibling-resource 3 / 3 3/3 shows which group prevails in a direct conflict. Comparing these conflicting conditions with the agreeing ones shows whether agreement between the groups strengthens adoption. File Identity. In the eight conditions, each intermediate support level uses one fixed assignment of the alternative to files; at local support 1 / 3 1/3 , for example, it appears in tasks_list (Figure 4 , “default”). Raising the support level therefore also changes which files carry the alternative, so example count and file identity are confounded. To separate them, we hold the support level fixed and vary only the placement: at 1 / 3 1/3 support, we place the alternative in the create, update, or list endpoint (Figure 4 , lower rows); at 2 / 3 2/3 support, in each of the three pairs of these endpoints. We first conduct this analysis exploratorily for ID serialization with one agent, including a control that changes only module registration and import order, and then replicate it in three further pair–agent settings (Section 4.3 ). We designate a target implementation and set all six existing endpoints to the opposite implementation, so that no file in the repository supports the target and any adoption must come from the guidance. In the running example, all existing endpoints serialize IDs as integers, whereas the target uses strings. The functional task and hidden tests remain unchanged. We compare four guidance conditions, all supplied in the initial task description: • C0 (no guidance): the task does not mention the target; this is the control. • C1 (written rule): a statement of the target and its priority over existing code, without code, such as “Serialize task identifiers as strings in the new endpoint. This instruction takes precedence over the ID representations used by existing handlers.” • C2 (code example): a snippet that demonstrates the target, such as "id": str(task.id) , without stating its priority. • C3 (rule and example): both C1 and C2. Comparing C1 with C2 separates stating which implementation should govern a new change from demonstrating what that implementation looks like; comparing C3 with C1 and C2 shows whether the two forms complement each other. A separate experiment varies the delivery channel: the same written rule appears either in the task description or in the harness’s native instruction file ( CLAUDE.md or AGENTS.md ), with the task description otherwise unchanged. 3.5 Measuring Outcomes We evaluate each generated edit on two separate outcomes. Functional success indicates whether the edit passes the pair-specific hidden tests, which accept either implementation; sessions that produce no implementation count as functional failures. Implementation choice indicates which alternative the edit adopts, determined by pair-specific classifiers that inspect the produced code. Outputs that use neither or both alternatives are reported as unclassifiable rather than assigned a label. For Stages 1 and 2, we report the adoption rate : the share of classifiable outputs that use the designated alternative. For Stage 3, where the task prescribes a target, we use a joint outcome that requires both functional success and adoption of the target. Separating the two outcomes prevents a passing test suite from hiding which implementation an agent selected. 3.6 Open-Source Repository Validation The controlled repository is small and written in a single language. We therefore test whether its central Stage 2 contrast, local versus sibling-resource precedent, also holds in established codebases. We select four open-source REST API repositories in Python, Go, and TypeScript and study two implementation choices that occur across their frameworks. In error handling , an endpoint either propagates a typed error to a central handler (P) or constructs the error response directly (D); for example, it may raise a not-found error that a central handler converts into a response, or build an HTTP 404 response itself. In response envelope , an endpoint returns either a flat JSON object (F) or the payload under a sole top-level data key (D). Following Stage 2, we rewrite the existing handlers of the resource being extended (local) and of an analogous resource (sibling) to an assigned pattern, independently of each other. This yields four configurations in which the two groups agree or conflict (e.g., PP, PD, DP, and DD, with the local pattern first); in a repository without a sibling resource, only the local pattern varies. The agent then implements a new local endpoint without guidance about the choice. We evaluate functional success with repository-specific hidden tests and classify the resulting implementation. Because each repository fixes the number and identity of its handlers, this study tests the influence of local versus sibling-resource precedent, but not the support level or file placement, for which the controlled repository remains the source of evidence.
We also test a Stage 3 counterpart in the same repositories. With every local handler returning a flat payload, we ask whether a rule in the harness’s native instruction file makes the agent wrap the payload of a new endpoint under a sole top-level data key, compared with a contemporaneous no-guidance control. Because each repository fixes its own handlers, this test measures the effect of the rule against real conflicting code, not the support level or file placement. 4 Evaluation We answer four research questions: • RQ1 (Default Preferences): Which implementation do coding agents choose among functionally equivalent alternatives without relevant repository precedent? • RQ2 (Local Precedent): How do implementation patterns in task-related code influence agents’ choices? • RQ3 (Sibling-Resource Precedent): How do patterns in sibling resources affect implementation choices, particularly when they conflict with local precedent? • RQ4 (Explicit Guidance): Can explicit rules or examples steer agents toward a specified implementation despite conflicting repository precedent? RQ1–RQ4 use the controlled repository; Section 4.6 tests the local-versus-sibling contrast of RQ2 and RQ3, and the effect of an explicit rule (RQ4), in open-source repositories. We run each pair on its zero-precedent repository (Section 3.2 ) with all four agents, for 360 trials. All 360 runs pass the hidden tests and are classifiable. Default Choices. Without repository precedent, agents serialize identifiers as integers, name response fields in snake_case , return the resource as a flat JSON object, name Boolean fields without an is_ prefix, construct error responses directly in the handler, and dispatch priority labels through a dictionary lookup (Table 3 ). In dispatch, the default is the designated alternative, which is why the corresponding zero-precedent cells in Figure 5 are shaded. The six defaults share one property: each is the most direct expression of the required behavior in Python and Flask. Agents return the model attribute as stored ( task.id , project_id ), return the payload without a wrapper, use the shorter Boolean name, handle an error where it arises, and map values through a lookup table. Each alternative instead adds a conversion, a wrapper, a naming convention, or an indirection that the task itself does not motivate. Choosing such an alternative therefore requires information from outside the task, which is precisely what repository precedent and task guidance supply. Consistency. The defaults are near-deterministic and agent-independent. Of the 360 runs, 359 choose the default, and 23 of the 24 pair–agent cells do so unanimously; the only deviation is a single Sonnet run on dispatch. All four agents, from two providers and running in two harnesses, share the same default in every pair. Differences among agents in RQ2–RQ4 therefore do not stem from different starting preferences. Defaults vs. Precedent. Repository precedent overrides these defaults. When all six existing endpoints use the implementation opposite the default, agents follow the repository in 359 of 360 runs: 299/300 in the five pairs whose default is the baseline (“Both alternative” in Figure 5 ) and 60/60 in dispatch (“Both baseline”). Dictionary dispatch, chosen in 59 of 60 zero-precedent runs, is chosen in none of 60 runs once every endpoint uses an if / elif chain. Answer to RQ1. Without relevant repository precedents, all four agents favor the same implementation in each of the six pairs: integer IDs, snake_case fields, flat responses, unprefixed Boolean names, errors returned directly in the handler, and dictionary-based dispatch. These default choices are nearly deterministic (359/360 trials). Yet when all existing endpoints use the opposite implementation, agents follow repository precedent in 359/360 trials. Implication: Implementation preferences measured without relevant repository precedents do not necessarily predict agents’ choices when extending existing code. Support Level. Adoption increases with local support. Pooled over six pairs and four agents, adoption of the alternative rises from 0% (0/360) without local support to 21% (74/359) at 1 / 3 1/3 , 49% (175/360) at 2 / 3 2/3 , and 96% (347/360) at 3 / 3 3/3 (Figure 5 ). Adoption never decreases with local support in any of the 24 pair–agent combinations, and Cochran–Armitage tests find positive trends for all six pairs with Sonnet ( p ≤ 5.6 × 10 − 5 p\leq 5.6\times 10^{-5} ) and Opus ( p ≤ 1.3 × 10 − 5 p\leq 1.3\times 10^{-5} ). The curves share a direction but not a threshold. A single local file suffices for Sonnet to adopt string IDs (10/15), centrally handled errors (8/15), and camelCase (7/15), whereas Boolean naming stays at or below 1/15 through 2 / 3 2/3 support for every agent and reaches 15/15 only at 3 / 3 3/3 . Response envelope never reaches full adoption for the Claude agents (Sonnet 8/15, Opus 9/15 at 3 / 3 3/3 ). Agents also differ in which pairs they respond to: at 1 / 3 1/3 support, Sonnet adopts string IDs more often than gpt-6-sol (10/15 vs. 1/15, Fisher exact p = 0.0017 p=0.0017 ), whereas for dictionary dispatch the order reverses (4/15 vs. 12/15, p = 0.0092 p=0.0092 ). File Placement. Holding local support fixed, changing which files contain supporting examples substantially changes adoption in three of four tested pair–agent settings (Figure 6 ). In the exploratory ID-serialization experiment with Sonnet, a single supporting file yields 1/15–10/15 adoptions depending on placement ( p = 9.6 × 10 − 4 p=9.6\times 10^{-4} ). Two of three replications confirm the effect: with gpt-6-sol , relocating two ID-serialization examples changes adoption from 0/15 to 15/15 (Holm-adjusted p ≤ 6 × 10 − 5 p\leq 6\times 10^{-5} ); with Sonnet, relocating one field-casing example changes adoption from 0/15 to 11/15 ( p ≤ 6 × 10 − 5 p\leq 6\times 10^{-5} ). The Opus ID-serialization replication shows no detectable placement effect ( p = 0.148 p=0.148 ). Placement can even outweigh example count. For field casing with Sonnet, one example in tasks_list yields 11/15 adoptions, whereas two examples in the other local files yield none. Where placement matters, the most influential configurations include tasks_list , although agents differ in how much supporting evidence they require. These results show that example frequency alone cannot explain the influence of repository precedent. Answer to RQ2. Local precedent strongly influences implementation choices: adoption rises from 0% without local support to 96% with full local support, with no decrease across support levels in any of the 24 pair–agent settings. However, at a fixed support level, changing file placement can shift adoption from 0% to 100%, with detectable effects in three of four tested settings. Implication: Example frequency alone is insufficient to characterize the influence of repository precedent. Our local–sibling comparison jointly varies task relatedness and repository location, so it does not distinguish their individual effects. The experiments control which precedents are available, not which ones agents attend to. The zero-precedent condition measures task-specific choices without relevant endpoint examples rather than context-free model preferences. Native instruction-file experiments evaluate rules loaded by the harness, not autonomous discovery. Our classifiers capture selected implementation patterns, and the outcomes concern implementation choice, not maintainability or overall code quality. Internal Validity. In the support-level experiments, example count and file assignment vary together. The separate placement analysis reveals sensitivity to file identity but does not explain the influence of tasks_list . The zero-precedent and precedent conditions were collected under different execution settings. Technical interruptions required retries and disrupted scheduling in RQ4. An initial misconfigured Opus file-placement run was excluded and rerun; open-source outcome audits also led to revised classifications and recapture of incomplete patches. These changes and the trial accounting are documented in the artifact. Finally, differences between agents cannot be attributed to models alone, as each agent combines a model with its harness. External Validity. Fifteen repetitions per cell characterize variability under fixed conditions, not across tasks or repositories. The controlled experiments use one Flask API task family. The open-source study extends the local–sibling comparison to four repositories in three languages, but covers only two implementation choices, with explicit guidance evaluated for one. Support-level and file-placement effects remain untested beyond the controlled repository. The placement and guidance experiments cover selected settings, and the study evaluates agents from two providers. 6 Related Work Coding Agents and Software Evolution. Code-generation benchmarks such as HumanEval and MBPP evaluate the functional correctness of standalone programs Chen et al. [2021] , Austin et al. [2021] . SWE-bench moved evaluation to resolving real issues in existing repositories Jimenez et al. [2024] , and agents such as SWE-agent Yang et al. [2024] , AutoCodeRover Zhang et al. [2024] , OpenHands Wang et al. [2025a] , and Agentless Xia et al. [2025] navigate, edit, and test codebases to resolve them. Recent work extends evaluation from isolated issues to the continuous evolution of a repository: SWE-Milestone Deng et al. [2026] and SWE-EVO Le et al. [2026] evaluate agents on multi-step, long-horizon evolution tasks, Needle in the Repo Zhu et al. [2026] diagnoses maintainability failures in agent edits that pass functional tests, and Pinna et al. Pinna et al. [2026] compare agents through pull-request acceptance. These studies ask whether agent changes succeed and remain maintainable. We ask which of several functionally acceptable implementations an agent selects, and what in the repository and task determines that choice. Repository Context and Conventions. Software is repetitive and locally predictable Hindle et al. [2012] , Tu et al. [2014] , and project-specific conventions can be learned from existing code Allamanis et al. [2014] ; LLM-generated code nonetheless deviates from human coding style Wang et al. [2025b] . Repository-level techniques retrieve or plan over cross-file context to improve generation and repository-wide edits Shrivastava et al. [2023] , Zhang et al. [2023] , Ding et al. [2023] , Wu et al. [2024] , Li et al. [2025] , Bairi et al. [2024] , and repository instruction files such as AGENTS.md change agent behavior without generally improving task success Gloaguen et al. [2026] . These approaches treat context as a means to correctness. We hold correctness fixed and vary the available context, isolating how local precedent, sibling-resource precedent, and explicit instructions each govern the selected implementation. Preferences, Conflicting Guidance, and Design Rationale. LLMs show systematic preferences in code generation, such as favoring Python and widely used libraries Twist et al. [2026] , and their in-context behavior depends on the choice, order, and position of demonstrations Zhao et al. [2021] , Lu et al. [2022] , Fei et al. [2023] , Liu et al. [2024] . When context contradicts what a model has learned, LLMs may follow either source Xie et al. [2024] , Xu et al. [2024] , and instruction-hierarchy work trains models to rank instructions by their origin Wallace et al. [2024] . We study the corresponding conflict in software evolution, where an agent’s default, existing code, and new task intent compete, and measure which prevails. In software engineering, design decisions are first-class artifacts whose rationale is often lost Jansen and Bosch [2005] , Liang et al. [2023] , Zhao et al. [2024] , Sharma et al. [2021] . Our results show that agents act on recorded decisions without their rationale, and follow explicit priorities once these are stated. 7 Conclusion As coding agents increasingly participate in software evolution, functional correctness alone cannot explain which implementation decisions they preserve or change. This study establishes implementation choice as a distinct dimension of agentic software engineering and yields three takeaways: (1) repository precedent overrides agents’ shared defaults; (2) where precedent appears can matter more than how often, as local code dominates sibling resources and file placement alone can decide adoption; and (3) new intent must be stated, not only demonstrated, as written priority rules redirect agents more reliably than code examples. Our findings call for evaluating not only whether agents produce correct changes, but how they reconcile past decisions with evolving intent.
