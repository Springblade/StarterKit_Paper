While coding agents have demonstrated strong performance on single-issue tasks, it remains unclear how maintainable their code is when future agents build on top of it, potentially leading to compounding downstream effects. We investigate how agent code compares to human code in these maintenance settings, presenting CodeThread , a framework to construct controlled experiments from repository-level coding benchmarks. Applying CodeThread to four frontier coding agents and four benchmarks, we find that agents are less effective at resolving tasks when building on agent code compared to human code, with task resolve rate drops of up to 13.1%. Regression analysis reveals that many traditional software engineering maintainability metrics do not explain this difference. Instead, the clearest signals are subtler behavioral differences in agent code, such as changes to input validation and error handling, along with differences in downstream code size and task difficulty. These findings highlight the need to evaluate coding agents not only by immediate task resolution but also by maintainability, and point to potential sources of downstream errors introduced by agent code. 1 Introduction Coding agents are increasingly integrated into software engineering workflows, with promises of “completing weeks of work in days” ( OpenAI, 2026a ) . Model capabilities on coding tasks have also improved rapidly, with state-of-the-art agents solving a growing share of repository-level benchmarks ( OpenAI, 2026b ) .
However, a patch that passes tests and is functionally correct may introduce structural complexity, brittle abstractions, or confusing implementation choices that only surface as failures when the code is extended or modified in downstream tasks (Figure 1 ). Figure 1: Two pieces of code both being functionally correct does not mean they are equally maintainable. An example instance where both the human and agent code pass the initial implementation task’s tests, yet when an agent makes a subsequent change to both, the version built on human code passes while the version built on agent code fails. This dimension of code quality is captured by maintainability , or how well the code can be modified and extended over time. Maintainability has been studied across many software development contexts, and static metrics have emerged to provide quantitative evaluations of maintainability. In particular, structural and size-based
metrics, such as cyclomatic complexity ( Ebert et al., 2016 ) ,
Halstead volume ( Halstead, 1977 ) , and cognitive
complexity ( Campbell, 2018 ) , have been used widely as proxies
for the maintenance cost of a project ( Riaz et al., 2009 ; Ardito et al., 2020 ) . The adoption of coding agents raises questions about whether code authored by agents is as maintainable as human-authored code. Recent work has measured agent code maintainability using these static metrics ( Wang et al., 2025 ; Orlanski et al., 2026 ) , but does not compare it with human code. Moreover, static metrics can often be confounded by codebase conventions and context ( Zhang et al., 2013 ) . To this end, we present CodeThread , a framework for controlled experiments to compare the maintainability of agent- and human-written code based on how well an agent can build on each. CodeThread transforms single-step, repository-level coding tasks (e.g., instances from SWE-Bench Jimenez et al. (2024) ) into two-step tasks comprising an initial implementation task and a dependent downstream task. CodeThread then constructs comparable agent and human code on the initial task while holding the downstream task author and test-based evaluation fixed, allowing us to isolate how authorship of the initial task affects downstream agent performance. We use CodeThread to evaluate four frontier models—Claude 4.5 Sonnet Anthropic () , GPT-5 OpenAI () , GLM 4.7 Zeng et al. (2025) ; Z.ai () , and MiniMax 2.5 MiniMax () —on four software engineering benchmarks spanning a range of programming languages and task types. We find that building on agent code leads to drops in downstream task resolve rates more often than building on human code, with gaps in resolve rate of up to 13.1%. Using code instances from CodeThread, we identify sources of differences in downstream task performance on agent and human code, performing a logistic regression analysis on cases where the two conditions produce different outcomes. We find that traditional static maintainability metrics generally do not explain these differences. Instead, the clearest predictors of cases where the downstream task fails on agent code but succeeds on human code are subtle differences in input validation and error handling. Larger downstream edits and task difficulty also help characterize where the two conditions diverge. Our contributions are as follows: 1. We introduce CodeThread, a framework for studying the maintainability of agent code through two-step pull-request chains. CodeThread applies to any SWE benchmark, making it scalable across task types and languages, and provides controlled comparisons of agent to human code. 2. Applying CodeThread to multiple frontier models and benchmarks, we show that agent code is overall less maintainable than human code, leading to worse downstream task performance. 3. We analyze the sources of maintainability differences between agent and human code, showing that traditional proxies such as structural complexity and verbosity do not fully capture these differences, which instead often arise from subtler behavioral effects. Together, CodeThread and our findings suggest that coding agents introduce maintainability costs that compound as their code is reused or extended in ways that current benchmarks and metrics fail to capture. We suggest directions for future work on the maintainability of agent code. 2 Related Work Figure 2: CodeThread framework. From the original benchmark instance, we construct a two-step task—an Implementation Task followed by a Follow-On Issue—producing three code states ( PR 0 \text{PR}_{0} , PR 1 \text{PR}_{1} , and PR 2 \text{PR}_{2} ) and three conditions: AA (agent performs both steps), HA (human performs the Implementation Task, agent performs the Follow-On Issue on human code), and HH (human performs both steps). Comparing AA and HA isolates the effect of agent authorship on maintainability, holding the follow-on author fixed. Evaluating Agents on Sequential Tasks. Several recent benchmarks evaluate coding agents on sequences of dependent tasks rather than individual issues.
CodeFlowBench decomposes Codeforces problems along their function-level dependency tree and requires the agent to implement each subfunction by reusing those it built in earlier turns ( Wang et al., 2026 ) .
SWE-Bench-CL orders GitHub issues chronologically within each repository to evaluate whether experience from earlier issues transfers to later ones ( Joshi et al., 2025 ) .
SlopCodeBench measures behavioral drift as agents repeatedly modify a codebase across long-horizon iterative trajectories ( Orlanski et al., 2026 ) .
In contrast, our work grounds measurements in real GitHub pull requests rather than fully synthetic problems or hand-authored projects. Additionally, by varying the authorship of an intermediate patch while holding the downstream task fixed, we isolate the maintainability cost of agent-written code from the inherent difficulty of sequential development. Maintainability of LLM-Generated Code. Large-scale GitHub analyses report rising code churn and duplication coinciding with AI-assistant adoption ( Harding and Kloster, 2025 ; Cynthia et al., 2026 ; Huang et al., 2026 ; Liu et al., 2026 ) , static analyses find that LLM-generated code exhibits more code smells than human-written code ( Paul et al., 2025 ) , and recent work shows that non-functional quality and design-constraint compliance degrade even when agent-generated patches pass tests ( Sun et al., 2026 ; Yu et al., 2026 ) .
Prior work has also measured code-quality degradation in sequential tasks.
MaintainCoder applies synthetic requirement changes to competitive-coding tasks and measures post-modification correctness alongside static metrics such as Cyclomatic Complexity and AST similarity ( Wang et al., 2025 ) . SWE-CI uses test pass rates over iterative edit trajectories as a maintainability proxy, treating later-stage pass rate as evidence of how well early decisions support subsequent maintenance ( Chen et al., 2026 ) . Our study instead measures maintainability directly through downstream issue-resolution performance. Rather than relying primarily on static proxies or synthetic requirement changes, we ask whether an agent can successfully complete a dependent follow-on task when the intermediate code it inherits is written by an agent versus a human, creating controlled experiments to measure the effect of authorship. The resulting code can also be analyzed using static metrics and failure-mode annotations, as performed in Section 5 . 3 CodeThread We introduce CodeThread, a framework for measuring the downstream effects of building on agent code in comparison to human code (Figure 2 ). CodeThread transforms standard single-issue software engineering benchmark instances into dependent two-step pull-request chains (Section 3.1 ), allowing for controlled comparisons of downstream outcomes across authorship conditions (Section 3.2 ) with evaluation built in (Section 3.3 ). CodeThread starts from an existing issue-resolution coding benchmark where instances consist of a written issue, a base commit, a human-authored ground-truth patch, and a test suite to determine whether the patch resolved the task.
Example benchmarks that follow this format include SWE-Bench Verified ( Chowdhury et al., 2024 ) , SWE-Bench
Multilingual ( Khandpur, 2025 ) , SWE-Bench
Pro ( Deng et al., 2025 ) , and FeatBench ( Chen et al., 2025 ) . 3.1 Step 1: Create a Two-Step Task From each benchmark instance, we construct a two-step chain consisting of two dependent tasks and three code states: the Implementation Task and Follow-On Issue , and code states PR 0 \text{PR}_{0} , PR 1 \text{PR}_{1} , and PR 2 \text{PR}_{2} . To create the first state, PR 0 \text{PR}_{0} , we remove the target function bodies while preserving their signatures, leaving a skeleton version of the benchmark’s initial code state. This provides a starting point from which different authors can implement the intended functionality, similar to the use of skeleton code in prototyping, where an initial code structure is later fleshed out with implementation details Ryoo et al. (2008) ; Queirós (2013) . The Implementation Task ( PR 0 → PR 1 {\text{PR}_{0}}\rightarrow{\text{PR}_{1}} ) produces human and agent implementations of the same task. Using an LLM, we create an issue asking the author to restore the missing functionality in the skeletonized code. This issue is provided to the agent, which implements the requested functionality to produce the agent PR 1 \text{PR}_{1} . We filter out PR 1 \text{PR}_{1} solutions that have already solved the benchmark issue by requiring them to pass all Pass-to-Pass tests, confirming that the original functionality is restored, while still failing all Fail-to-Pass tests, confirming that the downstream issue is not yet resolved. This ensures that the agent PR 1 \text{PR}_{1} reflects the benchmark’s initial code state rather than a partial or complete solution to the Follow-On Issue; accordingly, the target methods are functionally equivalent across the two PR 1 \text{PR}_{1} versions. Although agents sometimes incidentally satisfy Fail-to-Pass tests while restoring functionality, the filter retains a large majority of instances. Appendix A shows the prompt used to generate Implementation Task statements, as well as the prompt given to models when solving it. The Follow-On Issue ( PR 1 → PR 2 \text{PR}_{1}\rightarrow\text{PR}_{2} ) is the original benchmark issue applied on top of the PR1 implementation. The problem statement and testing criteria for the Follow-On Issue are unchanged from the original benchmark, making it a downstream task whose difficulty may depend on the maintainability of the PR1 implementation. We evaluate whether the Follow-On Issue is resolved using the original benchmark test suite: a PR 2 \text{PR}_{2} solution is considered correct if it passes both the Pass-to-Pass tests, confirming that existing functionality is preserved, and the Fail-to-Pass tests, confirming that the original benchmark issue has been fixed. 3.2 Step 2: Set-up Authorship Scenarios Using the two-step issue resolution pipeline, we vary authorship on PR 1 \text{PR}_{1} and PR 2 \text{PR}_{2} , creating a total of three comparable authorship scenarios: human PR 1 \text{PR}_{1} followed by human PR 2 \text{PR}_{2} ( HH ), human PR 1 \text{PR}_{1} followed by agent PR 2 \text{PR}_{2} ( HA ), and agent PR 1 \text{PR}_{1} followed by agent PR 2 \text{PR}_{2} ( AA ).
The HH condition consists of the original developer’s PRs provided by each benchmark, acting as the human baseline against which the other conditions are compared. Comparing AA to HA isolates the downstream effect of PR 1 \text{PR}_{1} authorship on PR 2 \text{PR}_{2} success, allowing us to directly evaluate whether agent code imposes a maintainability burden on subsequent agent work in comparison to human code. We focus on the maintainability costs that agents incur when building on prior code, comparing the outputs from the AA versus HA scenarios, as a growing fraction of developers use AI agents to extend existing codebases ( Li et al., 2025 ) . The AH setting of a human performing the follow-on task on top of agent code would offer a complementary human-centric view (by comparing AH versus AA), but would require recruiting a substantial number of developers and is out of scope for this study. By keeping the PR 2 \text{PR}_{2} author fixed, CodeThread is scalable and can be applied to many existing issue-resolution benchmarks without additional data collection from humans. Following Xu et al. (2025) , we treat SWE-Bench Verified and SWE-Bench Multilingual as bug fix benchmarks. We use the native labels of each SWE-Bench Pro instance, and treat FeatBench as a feature-implementation benchmark. Models and Agent Configuration. In order to cover a breadth of model types, we evaluate four frontier models: Claude 4.5 Sonnet, GPT-5, GLM 4.7 and MiniMax M2.5, two proprietary frontier models and two publicly available open-weight models. We use SWE-Agent Yang et al. (2024) as the scaffolding framework for all models. We follow the standard evaluation protocol of the underlying benchmarks and run each pair (model, authorship condition) once per instance in order to maintain tractable computational costs while providing coverage across all benchmark categories. We provide further details in Appendix C . 4.2 Results Overall findings. Table 2 shows the PR 2 \text{PR}_{2} resolve rates under HA and AA conditions. The number of instances that pass the PR 1 \text{PR}_{1} filtering differs by model, so we compare models using the subset of instances shared across all models within each benchmark. Across these instances, we find that agents more often perform worse when building on agent code than on human code: AA generally underperforms HA, with drops in downstream resolve rate of up to 13.1%. Full scores for each model and benchmark are provided in Appendix B ; we observe a similar pattern in both the shared-instance analysis and the full per-model benchmark results. The largest drops occur for GLM 4.7 on SWE-Bench Pro, which contains longer, multi-file edits drawn from professional codebases, and with GPT-5 on FeatBench, a set of feature implementation tasks. We trace the source of the gap between HA and AA in Section 5 . We also observe four cases where AA matches or exceeds HA performance. These should be considered in light of benchmark-specific baseline performance and sample size. GPT-5 shows small positive gaps on SWE-Bench Multilingual (+3.1) and SWE-Bench Pro (+0.8), but these coincide with lower HA baseline performance on the benchmarks, suggesting that the gap may reflect a weaker ceiling rather than greater robustness to agent code. The clearest positive result, Claude 4.5 Sonnet on FeatBench (+6.2), occurs on our smallest overlap set of 16 instances, where a small number of cases can substantially shift the observed gap. (2025) . 5 Why does AA underperform HA? We observe that agents building on agent code generally perform worse than on human code. To investigate the drivers of this gap, we focus on discordant instances—i.e., those where HA and AA yield different outcomes on the task.
Across all four models and benchmarks, there are 454 discordant instances. 64.3% of these are HA wins (HA passes while AA fails), while 35.7% are AA wins (AA passes while HA fails). After excluding instances with incomplete features, our analysis includes 405 instances (64.7% HA wins, 35.3% AA wins). We extract features from PR 1 \text{PR}_{1} and PR 2 \text{PR}_{2} , detailed in Section 5.1 , and fit a logistic regression model to identify which features most strongly predict whether HA or AA won in a discordant instance. 5.1 Features We use four feature categories to identify the root causes of the gap: static maintainability metrics to test traditional code-quality signals, patch localization features to compare the files and functions edited, behavioral drift labels to capture differences missed by static metrics, and an instance difficulty score to control for task-level variation. We describe each below and provide implementation details in Appendix D . Static maintainability metrics on PR 1 \text{PR}_{1} and PR 2 \text{PR}_{2} . Our first feature set comprises four static proxies for maintenance cost based on software engineering literature ( Riaz et al., 2009 ; Ardito et al., 2020 ) , spanning two dimensions of code quality.
The first dimension is structural complexity , for which we use Cyclomatic Complexity (CC) ( Ebert et al., 2016 ) , which counts linearly independent paths through a function, and Cognitive Complexity (CogC) ( Campbell, 2018 ) , which penalizes nested control structures.
The second dimension is verbosity , for which we use Halstead Volume (HV) ( Halstead, 1977 ) , based on operator and operand counts, and Logical Lines of Code (LLOC), which counts executable statements. For each metric, we compute two features per discordant instance: the AA–HA delta at PR 1 \text{PR}_{1} and PR 2 \text{PR}_{2} . Patch localization features on PR 2 \text{PR}_{2} . Our second feature set measures files and functions that the agent edits.
Prior work has shown that localization is one of the leading failure modes for coding agents ( He and Roy, 2026 ; Liu et al., 2025 ) . We focus on PR 2 \text{PR}_{2} because the PR 1 \text{PR}_{1} prompt explicitly lists the files and functions each chain must edit. The PR 2 \text{PR}_{2} problem statement does not, and the agent can freely choose which files and functions to edit.
We measure this with two Jaccard overlaps: one over the set of edited files, and one over the set of edited functions. Higher values indicate that the HA and AA patches modify more similar parts of the codebase. Behavioral drift labels on PR 1 \text{PR}_{1} . The third feature set captures differences between agent and human PR 1 \text{PR}_{1} s not reflected in aggregate static metrics. We develop a ten-category taxonomy for forms of behavioral drift, detailed in Appendix D.3 , and use Deepseek-V4 Pro ( DeepSeek-AI et al., 2026 ) as an LLM-judge to label instances by category.
We are particularly interested in cases where the agent’s PR 1 \text{PR}_{1} alters input-validation or error-handling behavior, which we define as input/error contract (IEC). From our observations, differences in exception types or swapped defaults can silently creep into the codebase. Agents may add an extra input-gating check that raises ValueError or use getattr with None as the default, while the human PR 1 \text{PR}_{1} would raise an error. In both cases, neither static metrics nor patch location features would distinguish the agent from the human code. Appendix D.7 shows five such cases contrasting the human and agent implementations of PR 1 \text{PR}_{1} and PR 2 \text{PR}_{2} .
As such, we look at whether or not the behavioral drift was labeled as one of three IEC categories—Input Gating, Silent Fallback, and Error Handling—setting the feature to 1 if so, and 0 otherwise. To verify LLM-judge accuracy, we manually check a subset of 50 LLM-judge labels (Appendix D.5 ). Instance difficulty control. We add a difficulty control to ensure that HA is not winning simply because it is evaluated on easier tasks. The model recovers a modest but reliable signal (McFadden R 2 = 0.069 R^{2}=0.069 , LR χ 2 ​ ( 18 ) = 36.1 \chi^{2}(18)=36.1 , p = 0.007 p=0.007 ) suggesting that these features are informative signals of downstream success, but do not fully explain or predict it. Figure 3 corroborates these results as static maintainability metrics show near-identical distributions on HA wins and AA wins, while IEC drift, Δ ​ LLOC PR 2 \Delta\text{LLOC}_{\text{PR}_{2}} , and instance resolve rate show the clearest visual separation between the two groups. This yielded the same three significant features with comparable odds ratios (IEC: OR = 1.70 =1.70 , p = 0.039 p=0.039 ; see Appendix D.6 for further details). Does PR 1 \text{PR}_{1} drift cause the unresolved outcome in PR 2 \text{PR}_{2} ? The IEC coefficient in Table 4 establishes the population-level signal, but population-level evidence does not tell us whether the drift was actually the cause of failing to resolve a given instance. We further investigate the cause of failures in the AA scenario, focusing on IEC for per-instance attribution as the only significant predictor in our model that identifies a specific, code-level mechanism. Δ ​ LLOC PR 2 \Delta\text{LLOC}_{\text{PR}_{2}} is a summary statistic and instance difficulty is a control variable, neither of which corresponds to a verifiable property of the agent’s PR 1 \text{PR}_{1} . We consider two scenarios that could decouple IEC drift from the downstream failure. First, the agent may rewrite the function containing the PR 1 \text{PR}_{1} input/error-contract divergence in PR 2 \text{PR}_{2} , removing the drift before evaluation. Second, the drift may persist into PR 2 \text{PR}_{2} , but the failing test may be evaluating a different part of the code. We use an LLM-judge (DeepSeek-V4 Pro) to attribute whether the failing test falls under either of these scenarios. The LLM-judge is given the PR 1 \text{PR}_{1} behavioral drift label with the generated rationale, the AA PR 2 \text{PR}_{2} patch, and the AA test outcome. It judges whether the divergence persisted into PR 2 \text{PR}_{2} , and whether the failing test can be traced back to the divergence. Table A4 reports the breakdown. The first scenario is rare: PR 2 \text{PR}_{2} rewrites the divergent function on only 6.9% of instances, while the drift is unchanged in 85.9% of instances. On 20.6% of instances, the drift is judged to both persist and directly relate to the failing test case. The remaining 74.4% fail for reasons we have not isolated, and we leave this analysis to future work. The high persistence rate also suggests that on long-horizon tasks (i.e., chains longer than our two-PR setup), this drift could compound across PRs and degrade downstream resolve rates further. Our setup cannot test this directly, and future work should assess the effects of these drifts over long-horizon tasks. The full prompt and output schema are provided in Appendix D.4 . 6 Conclusion Across four benchmarks and four frontier models, building on agent code more often lowers downstream resolve rates than building on human code, with effects varying by model and task type. These differences are not well explained by static maintainability metrics alone; the clearest code-level signal is subtle behavioral drift in agent code, while larger downstream edits and task difficulty also indicate where the conditions diverge. Thus, building on agent code often introduces maintainability costs, which appear even on two-step chains and are likely to compound over many edits of a software project. As agent contributions become a larger share of working codebases, evaluation must shift from isolated task completion toward long-term maintainability. Limitations We present limitations of our study. First, we consider only two-step pull request chains ( PR 1 → \rightarrow PR 2 ). Although this setup is sufficient to study whether the quality of an intermediate patch affects a downstream modification, it does not capture longer-horizon development trajectories, where technical debt may compound over multiple successive edits. Future work should explore constructing longer PR chains with function-level overlap across successive tasks. Second, we filter PR 1 \text{PR}_{1} by instances where the agent PR 1 \text{PR}_{1} did not already address the Follow-On Issue. This filtering is necessary for the two-step chain to be well-defined, maintaining the separation between the two tasks so that the effect of authorship can be evaluated in isolation from functionality. However, it may introduce selection bias, since restricting the analyzed instances to where the agent did not solve the Follow-On Issue at PR 1 \text{PR}_{1} may not represent the agent’s natural behavior across the full benchmark. Nonetheless, the filter retains a large majority of instances, and we verify that cases where the model satisfies Fail-to-Pass tests in the Implementation Task are often incidental. Third, as discussed in Section 3.2 , our work does not study the effect of human-authored PR 2 \text{PR}_{2} on top of agent-authored PR 1 \text{PR}_{1} (AH) setting. Doing so would allow for a comparison of how difficult it is for human developers to build on agent code versus human code, and provide a more human-centric analysis of code maintainability. However, constructing this condition at scale would require recruiting developers to author PR 2 \text{PR}_{2} across all instances, which is infeasible in our current setting and difficult to control due to factors such as familiarity with the codebase. Future work could examine the AH setting on a smaller curated subset. Ethical Considerations This work aims to support more reliable evaluation and deployment of coding agents by studying the maintainability of code produced by these systems. Our findings show that agent code can affect downstream maintenance, underscoring the need for benchmarks, review practices, and safeguards that evaluate coding agents beyond immediate task completion and support informed decisions about when and how to rely on agent code. These findings should not be interpreted as evidence against the use of coding agents broadly, but as a call for evaluations that better reflect the long-term effects on software development. D.4 PR 1 \text{PR}_{1} Error Compounding into PR 2 \text{PR}_{2} The PR 1 \text{PR}_{1} behavioral drift judge in Appendix D.3 identifies instances where Agent PR 1 \text{PR}_{1} diverges from Human PR 1 \text{PR}_{1} . A PR 1 \text{PR}_{1} divergence does not automatically mean the chain fails. Two scenarios can decouple it from the dwonstream failure. First, the agent’s PR 2 \text{PR}_{2} may rewrite the divergent function, replacing the drift with a different code block. Second, even when the drift survives, the benchmark’s unit tests may not exercise it. The question is therefore: did a PR 1 \text{PR}_{1} divergence persist into PR 2 \text{PR}_{2} ’s final state, and did it directly relate to the failing test case? D.5 Human Audit of the PR 1 \text{PR}_{1} Fidelity Judge We verify a stratified sample of the DeepSeek-V4 Pro judge’s outputs against the underlying code to assess the reliability of its IEC labels. We sampled 50 instances, with 56% labeled IEC and the remainder assigned non-IEC labels. Instances used as examples or illustrations elsewhere in the paper were excluded from the sample. Rare labels were over-sampled so that every label is represented. The sample spans all four models and all four benchmarks used in our evaluation. Samples range from 28 to 376 combined patch lines (median 109). For each instance, the auditor was shown the judge’s label and reasoning together with the human and agent PR 1 \text{PR}_{1} implementations of the same stubbed target functions. The auditor then determined whether the assigned label was correct using the same criteria specified in the judge prompt. We audit the judge’s labels rather than obtain independent blind annotations given the difficulty of the task—assigning a label from scratch often requires repository-specific knowledge beyond the patch itself, such as whether an attribute may take a false value, and the sample of 50 instances covers 29 distinct repositories.
As such, this procedure is a verification audit rather than an independent re-annotation, and we report confirmation rates. The IEC/non-IEC classification underlying our analysis was confirmed in 48 of 50 instances (96.0%). Seven of these moved an item between two labels on the same side of the boundary, leaving its IEC classification unchanged. The remaining two were reclassified from IEC to non-IEC, and no item was reclassified from non-IEC to IEC.
