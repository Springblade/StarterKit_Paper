### Concrete evidence possible without additional model trials

These are recommendations for the protocol, **not completed analyses or established findings**.

1. **Bound the comparative question.** Keep the two prespecified S/V contrasts on the same admitted task set. Display all 24 cells as counts out of two, missing outcomes, both repeats, and acceptance/preservation separately. Analyze time/tokens for all attempted runs. Domain-balanced descriptive summaries and leave-one-task-out contrasts can expose dependence on the chosen mix; they cannot create additional independent tasks or repair limited precision [E48-M2-M3, E48-P2, E48-P5].
2. **Improve and document workload coverage before outcomes.** Map each proposed task to its user operation, state change, permission boundary, public entry point, shared source surface, and preservation obligation. Naming six behavior types does not broaden a repeated billing surface. The revised plan proposes U03 (admin role assignment) in place of B01 (order-code lookup), using the same eight slots, to add a permission-sensitive state change and reduce overlap with the history development task. This improves proposed within-application breadth, but U03 remains pending public-contract review, existing-session semantics, reference/alternative implementations, and V-gate qualification. Equal family counts alone are not a reason to select it. No outcome-driven substitution, silently relaxed baseline, or claim of representativeness is justified [E48-M2].
3. **Audit the supplied suites on every saved assessable patch.** Freeze V0, V1, the hidden contract evaluator, the eligibility rules, and the escape definition before collection. In isolated resets, replay each suite on every saved patch from all four assigned conditions. Record all planned slots, suite errors, missing patches, and unassessable behavior. An offline V1 result for a V0 patch measures detection on that saved patch; it is not the agent outcome had V1 been supplied.
4. **Keep three questions distinct.** A primary preservation escape is **hidden preservation failure with all V1 checks passing**, among patches with both results assessable; report numerator/denominator and the full suite-by-hidden-result table. A hidden *new-feature acceptance* failure with old checks passing is not automatically a regression. A shared invariant omitted only on a new path needs its own predeclared label. For each escaped obligation, link the public request, actual handler/consumer, relevant checks, and assertion result. Record separately whether the path was exercised and whether its relevant behavior was asserted; include `unknown`. A file/line hit alone does not establish fault detection [E48-P1, E48-P3-P4].
5. **Use traces as auditable process evidence.** Fix an observable codebook before outcomes: supplied-check availability/use, relevant code access, added versus reused path, check-to-path connection, disclosed requirement omission, build/runtime failure, and unsupported/unknown. Keep an evidence index for every run, including successes and negative cases; choose at most one illustrative example per task by a declared rule. Link labels to command/output, patch, and evaluator evidence. Do not infer hidden reasoning or claim causal mediation from post-treatment traces. Author review is required for subjective labels; assistant assistance and absence of an independent second reviewer must be disclosed [E48-M1, E48-P1-P3, E48-P5].
6. **Qualify the oracle without tuning to observed agent failures.** Use the already planned correct reference, a meaningfully different valid implementation, and plausible hand-constructed fault variants on both layouts. Where feasible, include a fault on an old path and one on an alternative new implementation path for the same declared obligation. Publish the check-by-fault matrix and explicitly call seeded faults constructed probes, not observed agent errors. If later audit finds a scorer defect, version it and re-score every affected saved patch consistently; post-outcome new probes remain exploratory and must not be presented as frozen tests.

**Candidate contribution after evidence exists:** a reproducible, bounded comparison of source organization and supplied preservation checks, paired with a contract-to-execution audit explaining where those checks do or do not detect defects in the resulting patches. This is a conditional empirical extension or replication. Neither the factorial design, joint-success endpoint, trace taxonomy, nor repository manipulation alone establishes novelty [E48-P1-P5]. If no escapes occur or comparisons remain unresolved, report that result; the protocol must not depend on finding a favorable effect.

**Local feasibility evidence reported by the coordinating agent, not independently executed in this source review:** static inspection of installed Better Auth 1.6.25 found that its admin middleware obtains an authoritative session and `setRole` checks permission before updating the persisted role; the SmartKit guard uses `getSession` with a 300-second cookie cache. This motivates checking the caller's current server-side role on the new write path, including a demoted caller with an old cookie, while evaluating the target's changed permissions after fresh authentication. It does not establish runtime behavior, immediate invalidation of existing sessions, or task readiness; the plan must retain these distinctions.

**Still unverified:** complete comparator execution artifacts; SmartKit task admission, session/permission contracts and new-path oracle reach; telemetry completeness; independent review; main outcomes. This review neither authorizes nor launches additional model trials and provides no publication guarantee.

## Pre-run research-value verification — 15 November 2026

**Decision: revise the contribution statement, then proceed only after the existing non-model qualification gates pass.** The two starterkit choices remain a defensible empirical question. Current literature does not make their answer obvious, but this search does not establish that their combination is unprecedented. Forty-eight attempts can supply bounded observations and inspectable artifacts; neither their number nor the factorial label establishes sufficient information or publication value. This review does not authorize model execution.

**Practical decision and possible knowledge gain.** The decision is whether, for the selected SmartKit feature workload and one fixed agent/budget, to organize existing source by layer or feature and to ship additional executable checks of existing behavior. The useful observation is new-feature acceptance together with retained behavior and total attempt cost. A folder-layout preference, faster navigation, or passing visible checks alone does not settle that decision. The added suite is a package of readable examples and executable feedback; this design cannot identify those channels separately. These are interpretations of the proposed intervention, not established effects.

**Inference from these comparisons.** None of these five inspected methods is an exact test of layer-versus-feature grouping crossed with access to additional old-behavior checks. That is an absence within this targeted search, not evidence that no such work exists. The distinction matters only if the task implementations actually encounter the changed organization and risk changing behavior the extra checks observe. An exact combination of familiar factors is insufficient by itself; the research argument must connect the two deployable starterkit choices to those observable consequences. A replication or extension with this explicit scope can be worthwhile without universal novelty.

**Evidence required before spending the 48 attempts.** The current plan already requires the relevant checks; they remain unresolved until artifacts demonstrate them. Map each task's real public operation, applicable legacy obligations, and relevant logical modules across both layouts, including unchanged framework routes. Establish baseline parity and meaningful missing functionality, admit valid alternative implementations, and show that the evaluator observes the actual request/state transition. This establishes treatment reach and outcome validity without requiring the agent to edit a prescribed number of files. U03's runtime permission/session contract remains a local qualification issue, not something this literature review resolves.

The V-gate deliberately selects tasks for which a plausible existing-behavior fault is missed by V0 and detected by V1. Randomized V assignment can still answer the effect on that fixed, selected workload. The claim must state this enrichment: it cannot estimate a benefit over ordinary starterkit tasks in general, and the constructed-fault gate is not independent evidence of effectiveness on agent-generated patches. Avoid inventing remote regressions merely to make a task eligible. These limitations follow from the active protocol's selection rule.

**Value under unfavorable or null outcomes.** The result can still document the two contrasts and their uncertainty, where the agent actually used the changed modules/checks, and which frozen suites detect contract violations in assessable saved patches. A null contrast is inconclusive about equivalence. If all patches preserve behavior, defect-detection sensitivity on observed faults is not estimable; the constructed qualification faults remain a separate kind of evidence. If all attempts fail or the final comparison is uninformative, report the bounded failure/measurement result and reusable artifact. Do not promise a paper-level contribution merely because the scheduled runs finished, and do not require a positive effect or an escape to justify reporting the result. Offline rescoring measures the saved patch, not how the agent would have behaved with different feedback.
